三、发现的问题

★ P1（真 bug，已修）：非法查询参数导致连接被单方面断开

现象：GET /api/events?limit=abc ⇒ 客户端收到 RemoteDisconnected。

证据（web.log）：

File "server/web_server.py", line 98, in do_GET
    limit=int((q.get("limit") or ["100"])[0]),
ValueError: invalid literal for int() with base 10: 'abc'

为什么这条最阴：服务本身没事（/api/health 仍 200）， 但调用方看到的是网络层错误，无法区分「我传错了」和「服务挂了」。

修法：参数解析加容错 ⇒ 非法值返回 400 + 读得懂的原因； 并给 limit 加上限（MAX_EVENT_LIMIT = 1000）—— 没有上限时 ?limit=999999999 会把整张 events 表拉进内存。

同类问题一并修：do_POST 的 Content-Length 解析（同样的 int() 崩溃路径）。

修复后复测：

?limit=abc            400 ✓ （原来断连）
?since_seq=xyz        400 ✓
?limit=3              200 ✓ 3 条
?limit=999999999      200 ✓ 被兜到上限
?limit=-5             200 ✓ 取 0 条
(空)                   200 ✓ 默认 100

反向验证：把 try/except 撤掉 ⇒ test_events_bad_params_return_400_not_disconnect 立刻 ERROR ⇒ 判据有承载力。

P2（架构局限，未修，已记录）：多进程各自去重 ⇒ 重复提醒

现象：两个独立 Store 实例（= web 服务与 MCP server 的等价物） 对同一个停滞任务各发一条 waiting ⇒ 合计 2 条。

原因：_stall_notified / _session_ensured 是进程内集合。 同一进程内去重是好用的（测试验过：连调 5 次快照只响 1 次），但跨进程失效。

影响：OrbCue 会重复弹提示音。不影响数据正确性，属"多吵一声"。

修法方向（择一）：

  1. 把去重状态持久化（events 表或一个 sidecar 文件）
  2. 进程间选主：只让一个进程负责向 OrbCue 投递
  3. 让 OrbCue 侧按 source+session_id+状态去重（要改上游，不现实）

为什么这次不修：这是体验问题不是正确性问题，且三种修法各有代价 （持久化要动 schema / 选主要引入新机制）。先记录，等你决定。

观察（非缺陷）

  1. board_reset 不清事件表 —— 只清 tasks，events 全保留。

这是对的设计（复盘证据不该被清）。 副作用：reset（或恢复）后，该任务的"最近活动时间"被 delete 事件刷成"现在" ⇒ 停滞检测重新计时。实测中 stalled: 3 → 0 就是这么来的。

  1. /api/events 的返回契约是 {"events": [...]}，不含 count ——

我第一轮断言写错（假设有 count）导致一条"假失败"。产品没问题。
