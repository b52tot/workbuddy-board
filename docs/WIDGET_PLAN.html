看板桌面挂件 —— 实现方案

日期：2026-10-05 ｜ 目标：把看板做成常驻 Windows 桌面的挂件
需求：① 无任务自动最小化、有任务自动展开 ② 树状展示、展开节点看细节 ③ WorkBuddy 启动时自动载入并保持同步

〇、先说三个必须拍板的事实

事实 1：现有数据模型里没有树

现在的结构是平铺的两层：

columns (todo/doing/blocked/done)
  └── tasks (position 决定同列排序，但**没有 parent_id**)

tasks 表字段（实测 data/board.db）：

id, title, description, column_id, position, priority, tags,
fields(json), created_at, updated_at, started_at, finished_at

没有 parent_id，没有"步骤"。 所以"树状展示"必须先回答一个问题： 树的节点是什么？ 这有三个答案，代价差很多（见第五节）。这是本方案唯一需要你拍板的点。

事实 2：树如果要"实时"，就不能每秒重建 DOM —— 这个坑今天刚踩过

web 端今天刚修一个 bug：renderBoard() 每秒 innerHTML= 重建全部卡片， 导致人手点击被吞（mousedown 落在旧元素、mouseup 落在新元素 ⇒ 浏览器不派发 click）。

原子点击（自动化测试）    ⇒ 弹窗打开 ✓     ← 测试一直是绿的
人手慢点击（按住 1.3s）   ⇒ 弹窗不打开 ✗   ← 只有真人能复现

修复：内容未变不重建（重建次数 6 次/6 秒 → 0 次）+ 事件委托（监听器只绑一次）。

挂件必须沿用同样的纪律：树每秒重建会丢失展开状态、滚动位置、选中项， 比点击被吞更烦人。方案里给了具体做法（第七节）。

事实 3：本机技术选型有实测答案，不用猜

磁盘上就有一个跑了很久的挂件：C:\llama.cpp\llama-monitor.ps1（3530 行，PowerShell + WinForms）。

手边的成功案例，第一身份是"技术选型答案"，第二身份才是"样式参考"。 所以本方案直接沿用它的技术栈，并复用其全部踩坑结论。

一、技术选型

结论：PowerShell 5.1 + WinForms + 原生 TreeView

候选置顶圆角无边框本机可用性判定
PowerShell + WinForms✅✅✅ 已有同款在跑，且能被自测验证选用
HTA (mshta)❌ 无置顶 API✅❌ 本机 mshta 被 LOLBin 策略拦，双击无反应排除
Electron / Tauri✅✅⚠️ 可用排除（技术理由见下）
Python + tkinter✅弱✅排除（圆角/拖动/DPI 要不偿失，而项目本体是零依赖 Python，挂件没必要再拖一个 GUI 依赖链）
关于 Electron 的说明（避免沿用过期前提）：
我记录里有过「用户明确反对 Electron」这条，该依据已于 2026-09-25 失效
（当日你已采用 Electron 版 dsh 桌面端）。所以本方案不是以"你反对 Electron"为由排除它，
而是纯粹的技术取舍：**体积 8.6MB→150MB+、内存 130MB→300MB+，换来的能力（复杂 DOM 树）
原生 TreeView 已经够用。** 如果你更看重 UI 表现力，这条可以推翻重选。

为什么不用 C# 编译（Add-Type -OutputAssembly）： 技能里记了这条路（675KB 原生 exe、无 Job Object 问题）。它适合"要交付单个 exe"的场景。 本项目第一版先跑通，打包留到第九节。

二、进程与生命周期模型

开机自启（启动文件夹 .lnk）
   │
   ▼
widget.ps1  ── 抢单实例互斥锁 Local\BoardWidget.RunOnce
   │            （锁建在 **ps1 自己**身上，不是建在启动器身上 —— 见下）
   │
   ├─ WorkBuddy 进程在跑？ ──否──▶ 最小化态（省资源，低频轮询）
   │                          └是
   ├─ 活跃任务数 > 0？ ──────否──▶ 最小化态
   │                          └是
   ▼
展开态（高频轮询 + 完整树）

★ 单实例锁必须护住"被交付对象本身"

技能里记了一个翻车案例：锁建在启动器 exe 身上，启动器 spawn 完 ps1 就退出 ⇒ 锁随启动器消失、ps1 还在跑 ⇒ 用户再双击又起一个 ⇒ 两个挂件并发写同一个日志 （症状：日志里同一事件出现两次、计数序列不连续）。

正确做法：锁建在 .ps1 上，且只读通道（-Probe/-SelfTest/-Render）不抢锁 —— 否则挂件在跑时跑一次自检会把它杀掉。

退出留痕：会话标记（因为硬杀写不出日志）

taskkill /F 走 TerminateProcess，不经托管层，一行日志都写不出来。 所以：启动时写 RUNNING，finally 里翻成 EXITED。 硬杀时 finally 执行不到 ⇒ 标记停在 RUNNING ⇒ 下次启动读到即判"上次异常退出"。

三个必须做对的细节（技能实测）：

  1. sessionOwned 闸门不可省 —— 只读通道写 EXITED 会把正在跑实例的 RUNNING 翻掉 ⇒ 漏报。
  2. 判据要测两个方向：漏报（真硬杀报正常）· 误报（正常关闭却一直挂提示）。
  3. 读旧标记必须在单实例"接管"逻辑之后 —— 接管会强杀旧实例，否则会把自己造成的

RUNNING 诬告成"上次异常退出"。

三、数据通道与同步机制

数据源：HTTP 轮询 127.0.0.1:8791

通道判定
HTTP /api/board✅ 选用。复用现有聚合逻辑（stats/stalled/进度），挂件不必重实现业务
直读 SQLite❌ 需 SQLite 驱动（非内置），且 stats 聚合要重写一遍 ⇒ 两份真相
subprocess 调 Python❌ 冷启动 Python 实测 200~700ms/次 ⇒ 太慢

三个接口（实测路由）

GET /api/board                                    → 完整快照
GET /api/events?limit=&task_id=&since_seq=        → 变更流水（★ 支持增量）
GET /api/health                                   → 探活

since_seq 增量是"保持同步"的正确机制：每次带上次的 server_seq， 只拉新增事件，不用每次全量。

★ 轮询必须"异步 + 分级"，否则 UI 会卡

技能里最贵的一条教训：Timer.Tick 在 UI 线程上同步执行，tick 里任何 HTTP 都会 整段阻塞消息循环 —— 菜单弹不出、拖动粘滞、按钮按不动。

实测对比（同一台机器）：CIM 查询 97~280ms、死端口 HTTP 900ms+（本机对未监听端口 不回 RST，而是静默丢弃 ⇒ 一直等到超时）。

方案：

态间隔理由
展开态2 s与看板 1s 刷新错开，够用且更省
最小化态15 s只需要知道"有没有任务"
服务不可达指数退避 2→4→8→16→32→60s 封顶避免每拍都在等超时

先 TCP 预检再发 HTTP（实测：死端口 TCP 预检 200ms 就能判定，比等 HTTP 超时快 6 倍）：

function Test-TcpPort([string]$h, [int]$port, [int]$timeoutMs) { ... }   # 见技能模板
if (-not (Test-TcpPort '127.0.0.1' $Port 200)) { 判服务不可达 }

⚠️ [Math]::Min(60, [Math]::Pow(2, $n)) 在 $n ≥ 32 时抛异常 ⇒ 返回 $null ⇒ $now.AddSeconds($null) 等于 $now ⇒ 立刻到期 ⇒ 退避失效。先按 double 算再转 int。

服务没起怎么办：挂件负责拉起

探 8791 不通
  ⇒ 判 workbuddy-board/svc.py 是否存在
  ⇒ 存在则 `python svc.py start`（CREATE_NO_WINDOW，绝不 DETACHED_PROCESS）
  ⇒ 起不来就在挂件上显示「看板服务未启动」（一等状态，不是空白）
⚠️ DETACHED_PROCESS 不能用（实测）：控制台程序拿不到控制台句柄会**静默退出、
返回 0、一行不执行** —— 用户看到的就是"双击无响应"。必须用 CREATE_NO_WINDOW (0x08000000)，
且子进程 stdout/stderr 重定向到文件，绝不用 DEVNULL（否则失败完全无声）。

四、树状结构的设计（★ 决策点）

三个选项

树的节点需要改数据模型吗说明
A列 → 任务 → 事件流不需要叶子 = events 表里该任务的流水（create/move/advance/update），"每一步"就是这条时间线
B列 → 任务 → 子任务需要（tasks.parent_id）像 kanban-mcp 的 epic→task，适合"大任务拆小"
C列 → 任务 → 阶段（step）需要（新字段 steps）结构化阶段："取凭证 → 执行 → 校验 → 完成"，对应待办里的 C4「阶段条」

我的推荐：先做 A，B/C 按需演进

理由：

  1. A 立刻可用、零改动。 事件流已经存在且信息量很大。实测你现在的任务就带着完整流水：
seq 6  move     doing → done
seq 5  advance  → 45/100
seq 4  update   fields.progress = {current:45, total:100, message:"上传中：第 45/100 个"}
seq 3  create   进入 doing

展开一个任务节点，看到的就是"它怎么走到今天的" —— 这正是"每一步"最直接的答案。

  1. B/C 的真实需求你还没表达过。 现在的任务（"下载「嘻咦啊看」全部视频"）是一条流水线，

不是"父任务带一堆子任务"。当前阶段信息记在 description 自由文本里 （"抓到 61 个，页面报 totalCount=70…"），有内容是结构化的。

  1. 按项目的既有原则：不引入一项能力，除非它是真实痛点的唯一解（不是"别人有我也要有"）。

如果你选 C（阶段条）

代价与做法（这样你能比较）：

// config.json 的 fields 里加一种类型
{ "key": "steps", "type": "steps", "label": "阶段",
  "values": ["取凭证", "抓列表", "下载", "校验", "完成"] }
  • 存储：tasks.fields.steps = {current: "下载", done: ["取凭证","抓列表"], detail: {...}}
  • MCP 加一个 set_step(task_id, step, detail)
  • 挂件树多一层：任务 → 阶段 → 该阶段的产物
  • 代价：schema 不变（fields 本来就存 JSON），但要动 config 校验、MCP 工具、前端渲染、

以及所有正在跑的任务需要补字段。

树的形状（以 A 为例）

📋 WorkBuddy Board                              服务 8791 ●
├─ ▼ 进行中 (1)
│   └─ ▼ 下载「马铃薯男爵」双UP全部视频           ▓▓▓░░ 4.5%
│       ├─ 11:23:45  create   进入 进行中
│       ├─ 11:24:10  advance  → 45/1000
│       └─ 11:25:02  update   进度 {current:45, total:1000}
├─ ▶ 待办 (2)
└─ ▶ 已完成 (0)

折叠态只显示计数（▶ 待办 (2)）—— 一眼看到全局，不被细节淹没。

五、自动展开 / 最小化

状态机（带滞回，避免临界抖动）

        ┌──────────────── 用户点「展开」 ────────────────┐
        ▼                                                │
   ┌─────────┐   active>0 且 WorkBuddy 在跑      ┌──────────────┐
   │  最小化  │ ───────────────────────────────▶ │    展开      │
   └─────────┘  持续 ≥3s                          └──────────────┘
        ▲                                                │
        └──── active==0 持续 ≥20s  或  用户点「收起」 ────┘

四个必须处理的设计点：

  1. 滞回（≥3s / ≥20s）：任务在 0/1 之间抖动时不能来回切换。

展开慢一点没关系，来回闪是致命的。

  1. 最小化 ≠ 隐藏：变成一个小条，仍可见：

`` ● 3 个任务 · 1 个停滞 `` 隐藏了用户就找不到它，然后会以为"挂件没跑"（技能里的判活陷阱就是这个病根）。

  1. ★ 手动覆盖期：用户手动收起后，N 分钟内不自动展开。

否则"我收起来它自己又弹开" —— 这是最常见的体验翻车点。 手动展开则立即清除覆盖。

  1. 尺寸变化后必须重新夹紧位置：窗口从 320×480 缩到 200×36，若在屏幕右下角，

旧坐标会让它探出屏幕外。技能里踩过这个（旧 position.txt 把窗口推出屏幕 144px，而粗判据判定"合法"）⇒ 必须 Clamp-Position 四边全夹，且正反两向断言。

展开/收起的视觉

  • 不做尺寸动画（第一版）。WinForms 逐帧改 Size 要自己写 Timer，

收益小、易出新的抖动问题。

  • 切换用 SuspendLayout/ResumeLayout 包住，避免中间态闪烁。
  • 记住展开态的位置和最小化态的位置各一份（不然会互相覆盖）。

六、WorkBuddy 联动

检测方式

Get-CimInstance Win32_Process -Filter "Name='WorkBuddy.exe'"

⚠️ 技能实测：CIM 查进程表约 56ms，查监听表约 560ms ⇒ 必须缓存 + 节流， 不能每拍都查。方案：30 秒查一次，结果缓存。

⚠️ 不要用 Get-Process 判存活（本机实测常返空值 ⇒ 会误判"进程已死"）。用 CIM。

"启动时自动载入"怎么理解

两种实现，我倾向后者：

做法判定
挂件平时不跑，检测到 WorkBuddy 启动才拉起❌ 需要另一个常驻的"看门狗"，反而多一个进程
挂件常驻，WorkBuddy 在跑 + 有任务才展开✅ 选用。零看门狗，且 WorkBuddy 没开时它自己缩成小条

配合开机自启（启动文件夹 .lnk，注意生成 .lnk 要走 技能 windows-lnk-shortcut-authoring，别手拼二进制 —— 手拼版实测"属性面板显示正常但双击无反应"）。

七、UI 线程保护与"不重建树"（今天刚踩过的坑）

树刷新必须保留展开状态

# 刷新前：记住哪些节点是展开的
$expanded = @{}
foreach ($n in $tree.Nodes) { if ($n.IsExpanded) { $expanded[$n.Tag] = $true } }
# 重建后：恢复
foreach ($n in $tree.Nodes) { if ($expanded[$n.Tag]) { $n.Expand() } }

更好的做法：更新而不是重建。 节点集合不变时只改 Text/ForeColor； 只有增删节点才 Nodes.Add/Remove。这样展开状态、滚动位置、选中项全都天然保留。

这与 web 端今天的修复是同一个原则：内容没变就别碰 UI。

树节点数量要有上限

看板可能有几百个任务。TreeView 塞 500+ 节点会明显变慢。 方案：每列默认只展开最近 N 个（N=20），其余折叠成 … 还有 37 个。

采样必须在 UI 线程之外

技能里最实用的一条：让程序自己量自己。

$sw = [System.Diagnostics.Stopwatch]::StartNew()
# ... 本拍全部工作 ...
Record-TickCost ([int]$sw.ElapsedMilliseconds)   # 超预算写日志，连续 3 拍超预算自动放宽间隔

好处：不依赖用户投诉。用户只知道"卡"，程序自己知道"哪一拍慢了、慢在哪段"。

菜单打开 / 拖动期间停采样

if ($script:paused -or $script:menuOpen -or $script:dragging) { return }

技能实测：右键菜单弹出时若还在采样，菜单会卡。且这类修复必须用行为断言验证 （置 menuOpen=$true 后调一次 tick，tick 计数不得前进）。

八、可测性设计（三个无头通道）

顺序很重要：先验"能不能跑起来"，再验"算得对不对"。

通道作用不抢锁
-Probe采一次真实数据打印后退出，不开窗✅
-SelfTest跑完界面构建 + 用合成数据驱动全部状态分支 + 布局断言，exit 0/1✅
-Render复用已建好的界面跑 N 拍 → dump 每个控件真实 Text/颜色 → 退出✅

为什么要有 -Render：截图证明不了界面文案

技能实测两条路都堵死：

  • CopyFromScreen 抓到的可能是应用自己的窗口（把挂件压住了）
  • PrintWindow(PW_RENDERFULLCONTENT) 对 WinForms + GDI+ 双缓冲窗口返回整块黑图

⇒ 直接读控件的真实 Text 属性，比截图更硬：既能抓"算错了"， 也能抓"逻辑算对了但没写进控件"这类截图看不出的 bug。

窗口真的起来的硬判据

# Python ctypes：EnumWindows 按 PID 过滤
# 正向：进程存活 + 类名 WindowsForms10.Window.* + 外框尺寸 == 设计尺寸
# ★ 反向 baseline：对一个绝不存在的 PID 枚举，必须得到 0 个窗口

反向 baseline 不可省 —— 若 PID 过滤写错，正反两向都会"通过"。

⚠️ 测量进程自己要先 SetProcessDPIAware()，否则读出的是被虚拟化的坐标 （物理 800×236 读成 400×118，会误判成"DPI 感知失效"）。

判据必须"撤掉修复就会失败"

每条判据都要做故意破坏的副本，跑它的 -SelfTest，断言必须报错。 技能里的样例：撤掉 TCP 预检 ⇒ "上游发现"从 421ms → 1889ms，断言如期失败。

⚠️ 顺手检查有没有"不管怎么改都通过"的假判据 —— 有就删掉，别留着安心。 （技能实测抓到过一条：断言"标签双缓冲为 True"，但 Label 本来就默认开 ⇒ 纯摆设。）

九、交付与运维

文件布局

%LOCALAPPDATA%\BoardWidget\        ← 状态与日志，不污染桌面/程序目录
   ├─ monitor.log                  运行日志（分步留痕 + 分段计时）
   ├─ session.txt                  RUNNING / EXITED 会话标记
   ├─ position-expanded.txt        展开态位置
   ├─ position-mini.txt            最小化态位置
   └─ widget-child.log             子进程 stdout/stderr（绝不用 DEVNULL）

<项目目录>\widget\
   ├─ widget.ps1                   挂件本体
   └─ start.cmd                    启动包装（启动文件夹的 .lnk 指向它）

桌面只放一个入口，别撒多个文件让人猜点哪个。

启动分段计时

用户说"启动慢"时，看一眼日志就知道卡在哪段，不用外部反推：

[启动] 参数就绪        累计   120 ms
[启动] 界面就绪        累计   690 ms
[启动] 窗口可见        累计   710 ms
[启动] 首次采样完成    累计  1020 ms

⚠️ 顺序判据：窗口可见 必须先于 首次采样完成。 技能里踩过：Add_Shown 里同步采样 ⇒ 窗口出现后那一秒界面僵死 （拖动断、菜单弹不出），而"窗口可见耗时"这个指标根本看不见它。 解法是 BeginInvoke 把首次采样排到消息循环之后。

打包（第二版再做）
