「引入开源项目 vs 自建」决策分析

日期：2026-10-05 ｜ 决策对象：面向 MCP Agent 的通用任务看板

〇、结论（先给答案）

## 维持自建。不引入开源项目。

一句话理由：三个候选项目的主线能力——多 Agent 并发原子抢占（overclick 的 Postgres 事务）、 人机校验分离（overclick 的 validated）、多用户角色权限（flow 的 scoped key）—— 在「一人单机串行」场景下全部空转；而我在意的两项能力（停滞检测、配置驱动状态机） 竞品恰好都没有。

决策依据（按权重）：

#依据类型
1R3 停滞检测：竞品无一同类实现，而这是本机最高频痛点（长耗时任务静默卡死）能力缺口
2R4 配置驱动状态机：换业务不改代码，竞品多把工作流写死在代码里能力缺口
3竞品的重型依赖不是缺陷而是其设计动因（如 overclick 要 Postgres 是为了并发抢占），对本场景无价值需求不重合
4自建已覆盖 R1–R5 全部，且 R1/R2 已实测通过沉没成本 + 已达成

关键假设：

#假设状态
A1只有一人、单机、串行使用✅ 你已确认
A2依赖/Docker/Node 都不是障碍✅ 你已确认
A3可以 fork 改源码✅ 你已确认
A4R1–R5 是需求的完整清单⚠️ 未逐条确认（本次最大不确定项）
A5目标机（内网 Windows）与开发机环境一致，pip 源可达✅ 已实测 —— 依赖全为纯二进制 wheel，--no-index 离线安装通过（见第三步）

触发反转的条件（任一成立即应重评）：

#条件应转向
T1进入多 Agent 并发（多个 Agent 同时抢同一个队列）overclick（它的主场）
T2需要多人协作 + 权限隔离flow（角色化 key）
T3出现 R1–R5 之外的新硬需求（尤其 R4 之外的工作流形态）重新全量评估
T4自建的维护成本超过它省下的时间（连续三个月净负）迁移到 kanban-mcp

落地后的最小验证步骤（按顺序，任一失败即回到决策）：

#验什么结果
1手感性：pip install kanban-mcp → 真实跑一遍✅ 完成 —— 45 工具、握手通过；但 items 表无任何进度/停滞字段，R3/R4 压根不做
2能力性：自建 R3（停滞）与 R4（配置切换）在真实任务上各触发一次✅ 完成 —— 四条正向 + 四条反向全部正确
3假设性：目标机能否装上依赖（A5）✅ 完成 —— 纯二进制 wheel，--no-index 离线安装成功
三步实测详情见 VERIFY-三步验证结论.md。 第 1 步的结果把理由变得更锋利：
竞品不是「R3 做得差」，而是数据模型里没有这个概念 —— 它的 45 个工具全服务于
issue 跟踪的流程位置，「一个任务跑到百分之几、多久没动」它无从表达。

一、真实约束与评估框架

你的三条要求重新定义了评分标准：

你的要求评估含义
能用就行，不设约束依赖数量、部署复杂度不再是扣分项。要看的是「开箱能解决多少问题」
可直接用，能改就改fork 改造是合法路径，源码固定不再是硬伤
只有我一人、单机串行并发/多租户/权限全部不需要。需要的只有：任务可见、进度可见、卡住能发现

由第三条推出真正的需求清单（这是评估的基准）：

#真实需求优先级
R1Agent 能通过 MCP 建卡 / 移卡 / 查卡必须有
R2我能看到「现在什么在跑、跑到哪」必须有
R3长任务卡住了能发现必须有
R4换业务（搬运 → 发布 → 评测）不用重写有最好
R5事后能查「谁在什么时候改了什么」有最好
—并发认领不需要
—多用户/权限不需要
—真实 token 遥测不需要
—依赖图/层级不需要

注意：R1–R5 里，自建方案已经全部具备。所以真正的问题不是「自建缺什么」，而是「开源方案能不能以更低的代价给到这些，以及额外给到什么」。

二、接入可行性（唯一的硬约束）

你通过 WorkBuddy 使用，所以能不能接入是硬门槛。查了 WorkBuddy 的 MCP 配置（~/.workbuddy/mcp.json），它同时支持两种传输：

// 方式一：stdio（本地子进程）
"motrix": { "type": "stdio", "command": "...python.exe", "args": ["...server.py"] }

// 方式二：http（远程/容器服务）
"firecrawl": { "type": "http", "url": "https://...", "headers": {"Authorization": "Bearer ..."} }

对照三个候选：

项目传输能否接入接入方式
multidimensionalcats/kanban-mcpstdio✅直接配 command + args，最简单
ustoppble/overclickStreamable HTTP + Bearer✅配 type: http + url + headers，与 firecrawl 同款
axis-love/flowJSON-RPC POST /mcp✅同上

结论：三个都能接。 把「HTTP-only」列为劣势是夸大——它只是多一个配置项，不是障碍。

三、方案逐项评估（按你的标准重排）

排序依据从「轻量」改为「开箱能用的程度 + 与 R1–R5 的匹配度 + 改造成本」。

方案一：multidimensionalcats/kanban-mcp（83★）—— 最可能直接能用

开箱情况

  • 接入方式：stdio，一条 pipx install + MCP 配置即可，最贴合 WorkBuddy
  • 开箱就有：40+ 工具、Web UI、活动时间线、父子层级、epics、标签、导出（JSON/YAML/Markdown）
  • 数据库：默认 SQLite，零配置（README：「The SQLite database is created automatically on first run」）

对照 R1–R5

需求它是否满足
R1 建卡/移卡/查卡✅ 40+ 工具，远超需要
R2 看进度⚠️ 有进度条，但只对 epic（README：「progress bars for epics」），普通任务待确认
R3 卡住能发现❌ 无停滞检测
R4 换业务不重写❌ 6 种工作流写死在代码里（issue/feature/epic/todo/question/diary）
R5 事后可查✅ Activity timeline（status changes + decisions + updates + git commits）

关键结论：R1/R5 白送，R3/R4 缺失。

劣势与具体补强方案

劣势 1：R3 停滞检测没有

  • 补强：这是我们已经写好并测试过的能力（list_stalled，基于 events.seq，双向判据齐全）。
  • 做法：fork 后加一个 MCP 工具。它的数据库是 SQLite，我们能直接读它的表结构；已有 60 个测试的实现可以直接移植。
  • 成本：低。这是自建资产反哺开源方案的最佳切入点。

劣势 2：R4 工作流写死

  • 补强：你接受「能改就改」，所以改源码是合法路径。它的工作流在代码里是「类型 → 流转表」的映射，改成读配置文件是局部改造，不是重写。
  • 成本：中。需要读一遍它的状态机实现。

劣势 3：40+ 工具对单用户是负担

  • 补强：不改造，选择性使用。工具多不强制全用，Agent 按需调用。这不是缺陷，是「用不到的功能闲着」。
  • 成本：零。

劣势 4：语义搜索需 140MB 模型

  • 补强：它是可选 extra（pipx install kanban-mcp[semantic]），不装就没有。零成本规避。

方案二：ustoppble/overclick（118★）—— 能力最强，但超出你的需求

开箱情况

  • 接入方式：HTTP + Bearer token（WorkBuddy 支持）
  • 部署：docker compose up --build，需 Postgres 16 + Node≥22 + pnpm + AUTH_SECRET
  • 开箱就有：人机分工闭环、真实 token/时长遥测、证据链交接、Done != Validated、32 工具

对照 R1–R5

需求是否满足
R1 建卡/移卡/查卡✅ 32 工具（含 task_claim / task_deliver）
R2 看进度✅ 最强：真实 token + 时长，非自报
R3 卡住能发现✅ task_heartbeat 机制天然覆盖
R4 换业务不重写⚠️ 有 project/mission 分层，但流转规则未确认可配
R5 事后可查✅ 完整闭环

它的能力几乎完美覆盖 R1–R5，且 R2 比我们强（真实遥测 vs 自报）。

但它解决的问题，你有一个不需要

它整个设计围绕「多 Agent 抢任务 + 人机验收分离」：

  • 原子认领（atomic claims）—— 解决多 Agent 并发 ⇒ 你不需要（只有你一人）
  • 三角色（请求者/执行者/验收者）—— 解决团队分工 ⇒ 你不需要
  • Bearer token + AUTH_SECRET —— 解决多用户访问控制 ⇒ 你不需要

代价清单（按你的标准，这些不再是「否决项」，而是「要不要为用不到的能力付费」）：

代价对你的实际影响
Docker + Postgres 16 常驻一台机上多两个常驻服务；内网 Windows 上 Docker 可用性未知
必须编译（up --build）首次拉起要等构建
AUTH_SECRET 必填一次性生成，但要妥善保存（重启复用，否则 token 全失效）
HTTP 接入需配 type: http（你会配，firecrawl 已是这么接的）
v0.1 成熟度上游仍在快速演进，需锁版本

劣势与具体补强方案

劣势 1：为一个不需要的问题付运维代价

  • 规避（推荐）：不用它。这些代价换来的是并发/权限/协作能力，而你的场景三者皆无。
  • 但这不等于「它不好」——如果你的场景变成「多个 Agent 并行 + 需要验收留痕」，它立刻从「过重」变成「正好」。

劣势 2：Docker 在内网 Windows 上未知

  • 验证方法：docker --version + docker compose version。一条命令就能确定这条路通不通。
  • 如果不通：不折腾（不要在内网 Windows 上装 Docker Desktop，坑深）。

劣势 3：进度是「测量的」，但需要 Agent 报

  • 细看 README：token 数由 Agent 读取自己的会话记录后上报（「the briefing tells the agent exactly how to read those numbers off its own session transcript」）
  • 所以它虽然叫「真实遥测」，根子上仍是「Agent 主动报」，只是报了更具体的东西
  • 补强：无需补强。这条只是澄清——它也没有魔法，只是上报内容更细。

方案三：axis-love/flow（7★）—— 能力匹配，但生态最小

开箱情况

  • 架构：单 FastAPI 进程 + SQLite，与自建方案最像
  • 接入：JSON-RPC POST /mcp
  • 开箱就有：5 列看板、依赖图、5 种角色密钥、human-required 标记、Ideas 收件箱、Markdown 导入

对照 R1–R5

需求是否满足
R1✅
R2 看进度⚠️ 无明确进度条
R3 卡住能发现❌ 无停滞检测
R4 换业务不重写❌ 5 列写死（"five columns with enforced role transitions"）
R5⚠️ 未确认

它解决的问题（角色权限、多人分工）你同样不需要。

劣势与具体补强方案

劣势 1：5 列写死 + R3 缺失

  • 补强：同方案一——fork 后改。但它的列数是硬编码在代码逻辑里的（不像 kanban-mcp 至少有 type 表），改造量比 kanban-mcp 大。
  • 成本：中偏高。

劣势 2：7★ 生态极小、8 个依赖

  • 补强：依赖问题在「不设约束」下不算问题。
  • 真正的风险：7★ 意味着几乎无社区。遇到问题只能自己读源码。而你自己就有一个能跑的实现——没理由换到一个更小、更不成熟的同类品上。

这一条是它相对自建最致命的比较：功能和架构都与自建高度重叠（都是 SQLite 单进程 + 看板），但自建已经跑通且有你熟悉的结构，换它等于用未知换已知，而它并未带来你需要的额外能力。

五、重新决策

结论

## 维持「自建」。
理由：在「一人单机串行」场景下，自建方案已覆盖全部 5 项真实需求，而开源方案要么缺关键项（R3/R4），要么为不需要的能力付代价。

这不是「因为没有开源项目能满足约束所以自建」，而是「现有开源项目解决的问题与我的问题不重合」。

决策依据

#依据证据
1自建已覆盖 R1–R5 全部，且 R3/R4 是它独有优势60 测试全绿；配置驱动换业务零代码改动；停滞检测双向判据成立
2kanban-mcp 虽生态最好，但缺 R3（停滞检测）与 R4（配置驱动） —— 恰是自建最强、最实用的两项README 实测：进度条仅 epic；6 种工作流写死
3overclick 能力最强，但核心设计（原子认领/角色/权限）全部服务于多 Agent 并发与人机分工 —— 你的场景皆无其 README 第一句即「hybrid human + AI-agent teams」
4flow 与自建架构重叠但未更强，且 7★ 生态更小同为 SQLite 单进程看板；5 列写死
5「引入」的真实收益是减少自研工作量；但 R1–R5 已在自建中实现，收益已兑现工具数 13 / 测试 60
