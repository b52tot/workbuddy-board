任务挂件 · 自建实施方案

日期：2026-10-05 ｜ 前置：WIDGET_PLAN.md（初版设计）、WIDGET_RESEARCH.md（31 个项目调研）、ORBCUE-接入可行性.md（失败复盘）
界面原型：widget/prototype.html（可直接打开，含 4 个状态）

〇、一句话定位

一个常驻桌面的窄条窗口，让你不打开浏览器就看清楚「有哪些任务、各自到哪了、哪个卡住了」。

唯一的成功判据：任务卡住时，你不用切窗口就能知道，并且知道是哪一个。

这条判据是从 OrbCue 的失败里长出来的。OrbCue 技术上完全接通
（sent=8 dropped=0），但它刻意不显示任务内容，所有任务在球上
都叫 "Workbuddy" ⇒ 用户看屏幕上是三条一样的东西 ⇒ 没有可用性。
所以本方案的第一原则是：内容必须能看出"是哪一个"。

一、边界：做什么，不做什么

以内容为主 = 把预算花在"信息可读"上，不花在"好看"上。

做不做（避免过度设计）
任务标题完整可读（2 行截断）❌ 多层嵌套树（用事件流水代替，够看且不为树改数据模型）
进度条 + 37/88 · 42% + 上报消息❌ 动画/过渡/渐变/多重阴影
停滞高亮（橙条 + 已 85 分钟无进展）❌ 桌面宠物 / 像素场景 / 装饰插画
点开看变更流水（每一步的时间与内容）❌ 内置任务编辑器（编辑走 MCP，看板只读是既有原则）
空任务时缩成小条（不消失）❌ 多屏/多显示器复杂布局
服务不可达时明确说（不是空白）❌ 托盘二级菜单、快捷键自定义面板
视觉与看板同一套 token❌ 独立设计语言（那正是上一版被吐槽"相去甚远"的原因）

二、调研结论逐条落地

不照抄结论，逐条说采纳什么、不采纳什么、为什么：

调研发现本方案理由
没有一个开箱即用（31 个项目全查过）自建没有能直接读"我的看板"的
Tauri 构建即得 NSIS/MSI（Chronica 11.7MB / PILLAR 3MB）⚠️ 暂不采用本机没有 Rust 工具链（实测 rustc: command not found），装它约 1GB；而产物体积在本场景不是关键
OrbCue 的失败：不显示内容 ⇒ 三条同名✅ 反向采纳本方案把"能看出是哪一个"当第一原则
task-dashboard 的 ETag/304 条件轮询✅ 采纳挂件 2 秒轮询一次 9KB 快照是浪费，304 后几乎没有流量
PILLAR 的 hover 预览 / click 展开✅ 采纳范式比"自动弹开"克制；本方案用"无任务自动收起 / 有任务展开"
PILLAR 的 idle 时轮询休眠✅ 采纳收起态降频到 15s
dsh-task-board 的父子任务树 + 边界字段❌ 不采纳要改数据模型（加 parent_id）；而现有事件流水已经能回答"它怎么走到今天的"，不为展示需求改数据模型
Task Tree 的父节点进度自动汇总⚠️ 暂不做同上，无树即无需汇总
Chronica 的数据是纯 JSON 可外部写➖ 不需要我们有自己的 HTTP API 与 MCP，比写别人格式更直接
agent-traffic-light 用 PID 判活✅ 部分采纳用在"看板服务是否在跑"上（探活），任务级判活仍用上报中断（无独立进程可查）
desk-widgets 每个 widget 是独立 HTML✅ 采纳内容层就是独立 HTML ⇒ 改样式不用重编译
ClawMonitor 的"点击穿透 + 预留屏幕空间"❌ 不采纳挂件是要点的（看详情），穿透反而不能用

三、功能清单（做什么 · 怎么呈现 · 怎么实现）

每一项都对应原型里的可见元素，不是抽象描述。

F1 · 任务总览

呈现顶栏右侧橙色胶囊 1 个卡住；下方 3px 蓝色完成率条
数据/api/board 的 stats.stalled / stats.percent
实现有停滞才显示胶囊（恒为 0 的数字不占位置）

F2 · 分列任务列表

呈现按列分组：▼ 进行中 1 WIP 1/5；点击组头折叠/展开
空列折叠成一行（▶ 阻塞 0），不占纵向空间
数据columns[] + tasks_by_column
实现列定义来自后端（不硬编码列名）—— 换业务只改 config

F3 · 任务卡片（核心）

呈现标题（最多 2 行）→ 进度条 → 42% 37/88 马铃薯男爵的画廊 37/88 · 0 失败 → 停滞条 → P10 acfun nas … 2小时18分
数据title / fields.progress{current,total,message} / priority / tags / started_at
实现进度条用 warn 色而不是 accent —— 与顶栏"完成率"必须一眼区分（"在动" vs "完成度"）

F4 · 停滞高亮（最值钱的一条）

呈现卡片左侧橙条 + 内嵌 ⚠ 已 85 分钟无进展
数据stalled_ids + 任务上的 idle_sec
实现直接用后端的停滞判定（90s 阈值，config 可调）；不自己算 —— 两边算会不一致

F5 · 任务详情（"展开看每一步"）

呈现点卡片 → 换到详情视图：键值对（所在列/进度/说明/标签/优先级/创建于/耗时）+ 变更流水（时间 · 事件类型 · 内容）
数据get_task + /api/events?task_id=
实现事件流水就是"每一步"——create → move → advance → update，且 seq 单调，是真历史而非推测

F6 · 自动收起 / 展开

呈现无任务 → 小条 ● 3 个任务 · 1 个卡住；有任务 → 展开；手动收起后 5 分钟内不自动弹开
实现滞回（展开 ≥3s / 收起 ≥20s）+ 手动覆盖期 —— 避免临界抖动来回闪

F7 · 实时同步（省流）

呈现顶栏心跳点（绿/红）+ 展开态刷新频率 2s
实现ETag/304：服务端给快照算 ETag，客户端带 If-None-Match；没变就 304 空响应。收起态降到 15s，失败按 2→4→8→…→60s 退避

F8 · 服务不可达

呈现红点 + 看板服务未启动 + 挂件连不上 127.0.0.1:8791 / 数据仍安全存在磁盘上 + [启动看板服务] 按钮
实现TCP 预检（200ms 内判定）→ 尝试 svc.py start → 失败保持此态
为什么重要挂件最容易翻车的不是显示错，而是空白——空白让人分不清"没任务"和"连不上"

F9 · 窗口行为

呈现无边框、置顶、可拖、位置记忆、隐藏于任务栏
实现Win32 窗口样式 + 退出时写位置文件，启动校验是否仍在工作区内（防多屏拔掉后跑到屏幕外）

F10 · 跳到完整看板

呈现顶栏 ↗ 图标
实现打开 http://127.0.0.1:8791

F11 · 深浅色

呈现跟随系统；内容层与看板共用一套 CSS token
实现prefers-color-scheme；token 直接复制看板的 [data-theme] 定义

四、技术选型

结论：.NET 8 WPF + WebView2 控件（宿主）＋ HTML/CSS（内容）

┌──────────────────────────────────────┐
│  WPF 窗口（无边框/置顶/圆角/拖动）      │  ← 约 120 行 C#
│  ┌────────────────────────────────┐  │
│  │  WebView2 控件                  │  │  ← 系统已装（154.0.4258.53）
│  │  ┌──────────────────────────┐  │  │
│  │  │ widget.html + widget.css │  │  │  ← 前端设计的产出物
│  │  │  ← 拉 /api/board         │  │  │     （专家可直接改）
│  │  └──────────────────────────┘  │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘

为什么是这个组合

候选判定
WPF + WebView2✅ 选用。本机 .NET 8 + WebView2 都已装（实测），零新增依赖；内容层是 HTML ⇒ 能完整复用看板样式、能承载富内容、专家产出可直接放进去
Tauri 2⚠️ 备选。产物更小（3MB vs ~15MB）、安装包内置（NSIS/MSI）；但要装 Rust 工具链，且体积在本场景不是痛点
PowerShell + WinForms❌ 内容展示能力弱（富文本/进度条/流式列表都要自绘）⇒ 与"内容优先"直接冲突
Electron❌ 体积/内存代价与"窄条挂件"不匹配
体积那笔账：WebView2 方案产出约 15–20MB（自包含 .NET），Tauri 约 3MB。
但内容是重点、分发对象是本机与少数同事，12MB 的差别换"零工具链 + 复用现成 CSS"是划算的。
若将来要公开分发且在意体积，再评估 Tauri —— 内容层（HTML/CSS）可以原样搬过去，不返工。

数据通道

挂件 ──HTTP──▶ /api/board（ETag/304）
              /api/events?task_id=（详情用）
              /api/health（探活）

不直读 SQLite：会与 web 服务形成两份真相；走 API 则复用后端已有的聚合逻辑（stats/stalled/progress），换业务也不用改挂件。

分发

  • 开发期：dotnet run
  • 交付：dotnet publish -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true

⇒ 单个 exe（依赖 .NET 8 桌面运行时，本机已装）

  • 需要"拷给别人就能装"时，再套 Inno Setup（Traycer 的做法）出一个安装包

五、界面设计

产出物：widget/prototype.html（可直接打开，顶部有 4 个状态切换）

状态尺寸说明
展开态320×487有任务时的默认形态

收起态320×136无任务时缩成小条
服务不可达320×266一等状态

设计决策（每一条都有理由）

决策理由
复用看板的 dark token上一版被吐槽"与看板相去甚远"。用同一套变量，视觉天然同源
进度条用 warn 色（橙），完成率条用 accent 色（蓝）两者语义不同（"在动" vs "完成度"），同色会混
停滞用左侧橙条 + 内嵌文字，不用红停滞≠失败；红色是错误色，用它会让人以为任务挂了
空列折叠成一行纵向空间是最稀缺资源
卡片标题 2 行截断，说明 1 行截断保住"看得出是哪一个"的同时不让单卡撑高
收起态是小条不是圆点圆点看不出信息；小条能直接显示"3 个任务 · 1 个卡住"
无动画挂件常驻，动画只在切换瞬间可见，价值低而干扰持续
服务不可达态和"无任务"态长得完全不同空白是挂件最常见的翻车方式

给前端设计专家的接口约定

专家改 widget/widget.css + widget/widget.html 两个文件即可，不需要碰 C#：

  • 必须复用看板的 CSS 变量（--bg/--surface/--line/--fg-2/--accent/--ok/--warn/--bad）
  • 数据契约固定：/api/board 的返回结构不变（见 README.md 的接口说明）
  • 必须保留的语义颜色：停滞=warn、完成=ok、失败=bad、进行中=accent
  • 产出自检：在 320px 宽下不出现横向滚动、标题不溢出、四态齐全

六、分阶段实施

阶段内容验收判据（可机械执行）
P1 骨架WPF 无边框置顶窗口 + WebView2 载入静态 HTML窗口起来、尺寸对、能拖动、位置记忆；反向：位置文件写屏幕外时启动要夹回
P2 数据拉 /api/board 渲染真实数据与 curl 拿到的 JSON 逐字段一致；无硬编码假数据
P3 四态展开/详情/收起/不可达四态都能触发；不可达时页面不得留空白
P4 收展状态机滞回 + 手动覆盖构造 0/1 抖动序列，断言不闪；手动收起后 5 分钟内不自动弹
P5 省流ETag/304 + 分级轮询内容没变时服务端返回 304（用抓包或日志验证，不是猜）
P6 分发dotnet publish 单文件在干净目录跑起来；exe 双击可用

纪律（沿用本项目既有做法）：

  1. 先跑通端到端拿粗结论，再精修
  2. 每条判据做注入式反向验证（撤掉实现必须失败）
  3. "参数没报错 ≠ 参数生效" —— 找功能性证据

八、明确不做的事（写下来防止后面被加回来）

  • ❌ 父子任务树（要改数据模型；事件流水已够）
  • ❌ 挂件内编辑任务（写操作走 MCP，看板只读是既有设计）
  • ❌ 动画/桌宠/像素场景
  • ❌ 多显示器复杂布局（只保证"位置不跑到屏幕外"）
  • ❌ 托盘二级菜单、快捷键自定义
  • ❌ 自动更新（先手动换 exe；需要时再说）
