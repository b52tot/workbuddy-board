挂件通用性 · 拓展路线图

日期：2026-10-05 ｜ 前置：WIDGET_SELF_BUILD_PLAN.md
目的：回答「通用性上还能往哪走」——并说清哪些不该走
本文不是待办清单，是取舍依据。 下面每条都给了"值不值得做"的判断，
照第七节那三个问题自己也能判。

〇、两类「套得住」各有对应原型（可直接打开看）

类别原型怎么开
直接套住（不加任何字段）widget/index.html#cover工作台里数据切到「多种任务形态」
加可选字段就套住widget/fields-demo.html双击打开，勾开关看实时变化

「直接套住」证明什么

data-cover.js 里放了 8 种任务形态，只用现有五要素、不加任何新字段：

形态靠什么表达
调研型（8B 模型选型）无进度 —— 靠标题 + 说明撑住卡片
代码开发（Rerank 优化）进度 43% · 3/7 项优化
数据迁移（kb.db → Milvus）进度 61% · 8210/13389
批量跑批（全量重算）进度 58% · 824/1410
评测跑批（49 题）进度 63% · 31/49
视频下载进度 42% · 37/88
硬件验证（NUMA）阻塞列 + 停滞标记
排障（已完成）finished_at + 耗时

关键验证点：那三个没有进度的任务（调研 / 阻塞 / 完成）也能显示得清楚 —— 说明卡片不是"只会画进度条"，标题 + 状态 + 时间本身就能承载信息。 如果某类任务在这里表达不出来，它就属于「要加字段」那一类。

「加可选字段」证明什么

fields-demo.html 做成开关式：勾一个字段，右边的卡片和详情实时变化。 你能直接看到"加这个字段，多出哪条信息" —— 比看表格直观得多。

字段没有它时有了它之后
failed「失败了」和「卡住了」在卡片上长得一样红条 ✗ 失败 2 次 · 批次 311 超时；批次 607 OOM
due_at只知道「跑了多久」，不知道「还剩多久」蓝条 ⏰ 还剩 4小时30分，超期自动转红
assignee多 agent 并行时不知道哪个是自己要管的标签 @agent-A，可据此过滤
steps只有 43% / 3/7，不知道走到哪一步卡片 ▤ 3/7 步；详情里 ✓批大小调优 ▶KV cache 复用 ○算子融合
artifacts只看到「完成」，看不到「产出了什么」卡片 📎 2；详情里列出 📎 压测对比报告.docx

为什么成本低：这五个字段全部可选、挂在任务自己身上。 没有它们时卡片照常工作；有它们时多显示一行。 不改列结构、不改流转规则、不动已有任务 —— 这正是它和「改数据模型」的区别。

一、先划边界：通用性的本质是什么

挂件的信息模型就五个要素：

标题 · 状态(在哪列) · 进度 · 时间(创建/开始/结束/静默) · 阻塞

能套进这五个要素的，就是通用的；套不进的，硬套一定难看。

能不能套住例子结论
✅ 直接套住代码开发、下载、批量跑批、评测、数据迁移已经能用
⚠️ 加可选字段就套住截止时间、产物、失败重试、执行者、子步骤值得做，成本低
⚠️ 要改结构依赖、周期性谨慎，收益/成本比差
❌ 套不住实时监控曲线、对话流、甘特/思维导图不要硬套

判断原则（以后自己也能用）：

加可选字段 ≠ 改数据模型。
前者向后兼容、不动现有任务；后者要让所有人跟着改。
优先加可选字段。

二、方向 A：任务形态拓展（加字段，成本最低）

这一类的共同点：只加可选字段，不动现有结构。

#拓展呈现为什么值得成本
A1失败 / 重试卡片上 ✗ 失败 2 次，详情里看上次报错下载、跑批、CI 都天然会失败重试；现在失败了和"卡住"看起来一样低
A2产物 / 附件详情里 📎 报告.docx 📎 日志（可点开）代码开发、评测类任务的价值就在产物上；现在只看到"完成"，看不到"产出了什么"低
A3子步骤清单详情里一组扁平静态步骤 ✓ 依赖编排 · ✓ 迁移 · ▶ 校验 · ○ 报告这才是"展开看每一步"的正解 —— 比树轻，只加一个数组字段低
A4截止时间⏰ 今天 18:00 前，超期转红很多事情有时间要求；现在只有"耗时"，没有"还剩多久"低
A5执行者 / 归属@我 / @agent-A，可据此过滤多 agent 并行时最需要 —— 一眼知道哪个是我要管的低
A6输入 / 输出位置📥 /vol2/1000/A站精华 📤 E:/报告.docx你现在的下载任务，路径只写在 description 里，卡片上看不到低

这六条的共同特点：都是在已有卡片上多一行，不改列结构、不改流转规则。

A3 值得单独说

之前明确否掉了「父子任务树」，理由是"不为展示需求改数据模型"。 但 A3 不是树 —— 它是一个扁平有序列表，挂在任务自己的字段里：

"steps": [
  { "name": "依赖编排", "state": "done" },
  { "name": "数据迁移", "state": "done" },
  { "name": "向量校验", "state": "running" },
  { "name": "出报告",   "state": "pending" }
]
  • 不要 parent_id、不要递归、不要显示树形缩进
  • 就是一列带状态的点，在详情里竖着排开

它比树便宜得多，而回答的是同一个问题："这东西进行到哪一步了"。 进度条回答的是"完成多少"，步骤清单回答的是"走到哪了"——两者不等价， 比如"3/7 步"比"43%"更能说明问题。

三、方向 B：数据源拓展（成本中等）

#拓展呈现判断
B1多看板切换顶栏下拉：本机 ▾ / 192.168.30.121 ▾⭐ 推荐。你有服务器上的看板，两个环境来回看是真实需求
B2远程看板数据源配 http://192.168.30.121:8791⭐ 与 B1 一起做；注意连不上时的提示要和"没任务"区分
B3多实例并排同时挂两个看板⚠️ 谨慎。桌面会被占满；B1 的切换更实用
B4异构源聚合（CI / 监控 / 工单）——❌ 不做。挂件会被推着长成"万能面板"，而那一定会失去焦点

B1+B2 的实际价值：你现在是"本机看板 + 远程服务器干活"的工作方式， 挂件只显示本机的，就漏掉了真正在跑的那个环境。

四、方向 C：交互拓展

#拓展呈现判断
C1卡片快捷操作悬停出现 ✓ 完成 ⏸ 暂停⭐ 推荐，但有前提：写操作走 MCP 是既有原则，挂件要写就得给一条受限的写通道（只允许几个安全动作）
C2过滤 / 搜索按标签、按执行者、只看卡住的⭐ 推荐（任务一多就需要）。可以很轻：只做"只看卡住的"这一个开关
C3新卡住时通知系统通知⚠️ 谨慎。OrbCue 的教训就在这 —— 提醒很容易变噪音。要做就只在"从正常变卡住"那一次响，不是每次刷新都响
C4拖拽改状态卡片拖到别的列⚠️ 谨慎。桌面挂件里拖拽的手感很难做好，而收益不如在 Web 看板里拖

C1 的前提值得强调：现在 allow_write=false，挂件是纯只读的。 要给写能力，应该是白名单式的几个动作，不是把整个写 API 打开。

五、明确不做（写下来防止被加回来）

不做为什么
❌ 实时监控曲线那需要时间序列，不是任务模型；套不住就别套
❌ 对话流 / 聊天记录又一个"套不住"
❌ 甘特图 / 时间线视图挂件只有 320-760px，甘特图在这个宽度里没有可读性
❌ 复杂树 / 依赖图已有结论：不为展示需求改数据模型
❌ 挂件内编辑任务全文编辑走 Web 看板或 MCP
❌ 多用户协作编辑单机工具，别引入协作复杂度
❌ 异构源聚合（CI/监控/工单）会让挂件失去焦点

六、优先级：如果只做三件

按 价值/成本比 排，前三名是：

排名拓展理由
1A1 失败/重试 + A2 产物现在"失败"和"卡住"长得一样 —— 这是信息缺失，不只是"不够通用"
2A3 子步骤清单用最低成本回答"走到哪一步了"，比树便宜得多
3B1+B2 多看板/远程看板你的真实工作方式是"本机 + 服务器"，现在只覆盖了一半

次选：A4 截止时间、A5 执行者、C2 只看卡住的。

七、一条判断原则（以后照这个用）

问三个问题：
1. 它能塞进「标题 + 状态 + 进度 + 时间 + 阻塞」这五个要素吗？
塞不进 ⇒ 大概率不该做。
2. 是加可选字段，还是要改结构？
改结构 ⇒ 先问"不改结构能不能回答同一个问题"。
3. 它是补上缺失的信息，还是多一种看法？
只是多一种看法 ⇒ 价值通常低于"补上缺失"。
A1/A2 命中第 3 条的"补上缺失"，所以排第一；
甘特图命中第 1 条和第 3 条，所以不做。
